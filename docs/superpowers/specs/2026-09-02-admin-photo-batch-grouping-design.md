# 后台照片按导入批次分组设计

日期：2026-09-02

## 背景

后台照片管理当前只按 `photos.sort_order, photos.id` 返回照片。照片来自多个导入批次时，列表会交错排列，无法判断哪些照片属于同一次导入。本次改动只调整后台照片管理的关联、排序和展示，不改变公开相册、照片发布状态或导入流程。

## 目标与范围

- 在后台照片列表中将照片按导入批次分组。
- 批次按导入时间从新到旧排列；同批次内保持导入文件的稳定顺序。
- 继续支持现有的地点/状态筛选、全选、批量复制、编辑、预览、单张删除和批量删除。
- 历史上没有导入批次关联的照片显示在最后的“未归类照片”分组。
- 不新增数据库表，不迁移既有照片数据，不影响其他照片列表接口的行为。

## 方案

采用现有照片数组接口增加可选批次元数据的方式，而不是新增嵌套接口。这样客户端仍接收 `AdminPhoto[]`，现有操作只需继续使用照片 id，不需要在筛选或删除流程中维护两套数据结构。

### 数据关联

导入 worker 完成项目时已经将源文件 checksum 写入 `import_items.checksum`，照片也保存同一 workspace 内唯一 checksum。PostgreSQL 查询通过 workspace 和 checksum 关联 `photos`、`import_items`、`import_batches`。

一张照片如果对应多个已完成的导入项目（例如被重复导入），只选择创建时间最新的批次，确保照片只显示一次。没有匹配项目的照片不丢失，批次元数据为空。

照片记录增加以下可选字段：

```ts
type PhotoImportBatch = {
  id: string;
  createdAt: string;
  itemCreatedAt?: string;
  sourceKey?: string;
};
```

`PhotoRecord` 和 `AdminPhoto` 暴露 `importBatch?: PhotoImportBatch`。这些是兼容性扩展，公开接口即使携带额外字段也不改变现有字段含义。

### 排序

数据库列表排序规则：

1. `importBatch.createdAt DESC NULLS LAST`；
2. 批次内 `itemCreatedAt ASC`；
3. `sourceKey ASC` 和项目 id 作为稳定并列排序；
4. 没有批次关联的照片最后按原有 `sort_order, id` 排序。

内存仓储使用相同的批次优先规则，并以批次 `items` 数组索引作为缺少项目时间时的稳定顺序，保证开发环境和数据库环境表现一致。

## 前端展示

`AdminPhotosView` 在现有筛选结果上建立分组视图：

- 分组 key 为批次 id；未关联照片使用固定的 `unclassified` key。
- 批次标题显示本地化导入时间和该组照片数量。
- 未归类分组显示本地化的“未归类照片”。
- 表头只显示一次，各分组复用同一行结构和已有编辑表单。
- 选择状态仍以照片 id 为唯一标识，因此跨批次全选、复制和删除行为不变。
- 筛选后只渲染有匹配照片的分组；分组顺序沿用后端返回顺序。

新增中文和英文文案，并使用现有 locale 设置格式化批次时间；时间格式化失败时回退为原始 ISO 字符串的可读部分。

## 错误处理与兼容性

- 批次关联缺失、checksum 为空或批次时间为空时，照片归入未归类分组，不阻断列表加载。
- 批次元数据为可选字段，旧内存 fixture、旧照片和旧 API 消费者无需修改即可工作。
- 关联查询使用 lateral 子查询限制为每张照片一条匹配记录，避免重复行放大和重复渲染。
- 删除照片后，现有级联删除和存储清理逻辑保持不变。

## 测试

- 内存仓储测试：多批次照片按批次分组，重复 checksum 归入最新批次，无批次照片排最后。
- API/仓储测试：验证 SQL 返回的批次元数据字段和稳定排序（在可用的数据库测试环境执行）。
- 前端组件测试：两个批次和一个历史照片显示为三个分组；地点/状态筛选后分组和选择状态正确。
- 回归执行现有 lint、typecheck、unit test、build 以及 Chromium Playwright 测试。

## 不在本次范围

- 不增加手工创建或重命名导入批次的功能。
- 不改变导入历史页面的布局和批次发布逻辑。
- 不为历史照片强行猜测导入批次。
