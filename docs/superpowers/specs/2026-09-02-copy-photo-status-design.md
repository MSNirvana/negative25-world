# 批量复制照片状态设计

## 背景

后台照片管理已经支持将第一张选中照片的定位、地址或评分复制到其余选中照片。现在需要增加独立的“复制状态”操作，用于批量同步照片的可见性状态。

## 目标

- 支持批量复制三种状态：已发布、仅自己可见、隐藏。
- 沿用现有批量复制接口、鉴权、源照片和目标照片规则。
- 复制完成后立即更新管理列表中的目标照片状态。
- 保持“复制全部数据”现有语义，不将状态隐式加入其中。

## 非目标

- 不新增独立批量状态接口。
- 不改变公开图库、个人中心或单张状态编辑的现有规则。
- 不复制照片的标题、描述、评分、地址或定位，除非用户点击已有对应操作。

## 方案

### API

将 `AdminPhotoCopyField` 扩展为：

```ts
type AdminPhotoCopyField = 'location' | 'address' | 'rating' | 'status';
```

现有 `POST /api/v1/admin/spaces/:slug/photos/bulk-copy` 接受 `fields: ['status']`。后端从源照片读取 `published`、`hidden` 和 `ownerOnly`，并将归一化后的组合写入每个目标照片：

| 状态 | `published` | `hidden` | `ownerOnly` |
| --- | ---: | ---: | ---: |
| 已发布 | `true` | `false` | `false` |
| 仅自己可见 | `true` | `false` | `true` |
| 隐藏 | `false` | `true` | `false` |

`ownerOnly` 同步更新照片元数据中的 `ownerOnly` 标记，确保数据库字段和既有公开性判断保持一致。目标照片仍排除源照片；不存在的目标进入 `skippedIds`；响应继续返回已更新的 `photos`。

### 前端交互

在后台照片管理批量操作栏中，在“复制评分”之后增加“复制状态”按钮。按钮复用现有 `copyFields` 流程：

- 选中少于两张照片时禁用。
- 第一张选中照片作为源照片，其余照片作为目标。
- 点击后请求 `fields: ['status']`。
- 成功后用响应照片替换列表项，保留当前选择，并显示成功提示。
- 失败时沿用现有错误提示和忙碌态。
- “复制全部数据”继续只复制定位、地址、评分。

中英文文案、按钮标题和无障碍名称一并补充。

## 数据流

```text
选择照片 -> 点击复制状态 -> 前端提交 sourcePhotoId/targetPhotoIds/fields: ['status']
        -> API 鉴权与校验 -> AdminService 读取源状态
        -> 更新目标照片 -> 返回 photos/skippedIds
        -> 前端替换目标行并显示结果
```

## 异常处理

- 源照片不存在、权限不足、字段或目标数量非法：沿用现有 API 错误响应。
- 目标照片不存在：跳过并返回 `skippedIds`，不阻塞其他目标。
- 目标更新失败：保留已成功更新的结果，前端只应用接口实际返回的照片。
- 状态组合按上述三种规范归一化，避免产生同时隐藏又公开或仅自己可见但未发布的矛盾状态。

## 测试

### API

- 分别以已发布、仅自己可见、隐藏作为源照片，复制到多个目标并断言三项状态及 `metadata.ownerOnly`。
- 断言源照片不被修改。
- 保留现有缺失目标的 `skippedIds` 行为。

### Web/E2E

- 批量操作栏显示“复制状态”。
- 单选时按钮禁用，多选时发送 `fields: ['status']`。
- 模拟接口返回后，目标照片状态选择框立即更新，且选择项保持不变。
- 检查中英文文案和按钮无障碍标题。

## 验收标准

管理员在后台选中两张或更多照片，点击“复制状态”后，第一张照片的可见性状态被准确同步到其余选中照片；列表即时反映结果，已有复制定位、地址、评分和删除功能行为不变。
